# 提示策略（NOTIFICATION POLICY）

> 用户口径（2026-11-18）：**无感自愈优先**。只有「无法解决」和「严重」的问题才打扰用户。
> 典型反例：测速失败不该弹 toast —— 用户既没有数据损失，也不需要做任何决定。

---

## 一句话判据

问三个问题，任意一个"是"才允许打扰用户：

1. **会丢东西吗？**（配置/未保存内容/用户输入） → 会 → 必须报
2. **用户需要做决定或无法继续吗？**（选配置、装驱动、提权） → 是 → 必须报
3. **重试也不会有用吗？**（需要人工介入：删文件、改权限、换路径） → 是 → 必须报

三个都是"否" → **静默**（只 reportError 记录日志，不弹任何 UI）。

---

## 三档（对应 store.ts 的 NotificationUi）

| 档 | UI | 适用 |
|---|---|---|
| A 静默 | 无（仅日志） | 瞬时/可自愈/可重试：测速失败与忙、路由切换中、helper 唤醒慢、资源占用、内核更新检查失败、订阅排序失败、主题落盘失败（自动重试一次后回滚） |
| B 轻提示 toast | 一句气泡，2~4s 自隐 | 有结果需要知情、但不阻塞：设置已保存、订阅更新完成、健康告警（启动项不健康）、用户主动操作的失败（导出/打开目录/复制失败） |
| C 模态 | 阻塞，必须点 | 破坏性操作确认、会丢数据、需要用户决策：无活动配置、wintun 缺失需装驱动、启动恢复失败、还原/删除确认、保存配置失败（用户会以为存了） |

---

## 具体归类（本轮按此口径收敛）

| 场景 | 档 | 理由 |
|---|---|---|
| 批量测速启动失败 / 状态机忙 | **A** | 按钮复位 + 节点格显示超时/失败即是反馈；无数据损失 |
| 单点测速失败 | **A** | 该节点自己的延迟位置显示"超时/失败" |
| 内核更新检查失败 | **A** | 瞬时网络问题，按钮 12s 后自动复位，可再点 |
| 主题模式落盘失败 | **A** | 自动重试一次；仍失败则回滚到切换前模式，界面与后端重新一致 |
| 订阅排序落盘失败 | **A** | 立即回拉后端顺序，列表自己"弹回去"就是反馈 |
| LAN CIDR / Network hosts 输入非法 | **A** | 内联红字已在输入框下方；只是阻止保存 |
| TUN 适配器 60s 仍未就绪（TUN_NOT_READY） | **B** | 后端静默阶梯已自行重试 60s 才发这条，含义是"自愈失败"，需要用户知情（2026-11-18 事故：这里静默会让界面彻底"卡住无反应"） |
| 设置保存失败（Tun/Network/LAN/Behavior） | **B** | 用户以为已存、实际没存 → 必须知情（但不阻塞操作） |
| 用户主动操作失败（导出/复制/打开目录/安装驱动/更新组件） | **B** | 点了没反应会被当成"卡住" |
| 流量清零失败 | **B** | 破坏性操作未生效，需要知道 |
| 无活动配置 / 需装驱动 / 启动恢复失败 / 还原备份 / 删除确认 | **C** | 需要决策或无法继续 |

---

## 落码约定

- 静默档统一写 `reportError(e, "模块.动作")`，保证可排查（错误进 console + 后端日志，不打断用户）。
- 后端通知走 `store.ts` 的 `NOTIFICATION_UI` 表 + `resolveNotificationUi`（按 code 优先，其次 level）。
  新增后端 code 时先在这里登记档位，不要直接在组件里弹。
- 禁止在 `catch` 里既不 reportError 也不提示（"吞异常"）；静默 ≠ 忽略，必须是"静默 + 留痕"。
- 同一失败不要在 3 处重复提示（内联 + toast + 日志选一处可见即可）。
